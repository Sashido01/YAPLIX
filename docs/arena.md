# YAPLIX Arena MVP — локальный общий рейтинг

Issue [#52](https://github.com/Sashido01/YAPLIX/issues/52). Изменения в отдельной
ветке; Draft PR не разрешает merge. Arena предназначена для доверенной частной
LAN. Нет регистрации, синхронного игрового мира или внешнего сервиса.

## Пользовательские игры

В production нет встроенной Arena-игры или key-free DEMO. Сначала создайте игру
через обычный генератор и сохраните её. Arena доступна только для сохранённой
пользовательской версии с явным score-v1 bridge; неподдерживаемой версии интерфейс
откажет с `ARENA_UNSUPPORTED`. Синтетические игровые HTML используются только
в тестах и не являются Arena-продуктом или LIVE-приёмкой.

Откройте сохранённую поддерживаемую версию и нажмите **Общий рейтинг**. Выберите
частную сеть телефонов и **Запустить новую Arena**. Участники подключаются к той
же сети, сканируют один QR, вводят разные ники и нажимают **Начать попытку**.


## Совместимость произвольного HTML

Существующая сохранённая версия не переписывается ради рейтинга. Автоматического
чтения DOM, OCR, Canvas `fillText`, глобальной переменной `score` или времени
игры нет: эти сигналы не доказывают честный итог партии.

Минимальный явный opt-in **score-v1**:

```html
<meta name="yaplix-arena" content="score-v1">
```

Маркер заявляет контракт, а не сертифицирует механику. Необъявленная версия
получает понятное русское объяснение («Рейтинг недоступен для этой версии. Нужна
Arena-совместимая версия со счётом и завершением партии.») с кодом `ARENA_UNSUPPORTED`
в тексте ошибки и в диагностике — сырой код поверх интерфейса не показывается, ошибка
не блокирует остальное приложение и панель комнаты можно скрыть.
Объявленная игра без корректных событий тоже не получает рекорд. При отсутствии
`game_ready` участник видит предупреждение; при финише без счёта сервер отказывает.

Для создания/редактирования укажите **Arena** или **общий рейтинг** в запросе.
В существующий generation prompt добавится контракт, без отдельного inference,
скрытого repair или изменения validator. При редактировании уже совместимого
HTML контракт сохраняется в prompt. Strict Canvas v2 остаётся: вся игровая UI
рисуется в Canvas/WebGL. Если идее не подходят числовой счёт и завершение,
контракт запрещает придумывать их ради допуска в Arena. LIVE-генерация такой
версии требует отдельного явного владельцем бюджета; в этой задаче её не запускали.

Игра использует существующий Events v1 bridge:

- Получает от `parent` единственный `yaplix_init` с `protocolVersion:1`,
  `sessionId`, `versionId`; HTTP token и cookie игре не передаются.
- Через `parent.postMessage({channel:'yaplix',event}, '*')` отправляет
  `game_ready` (sequence 0), затем на реальном Start `game_started` (sequence 1),
  один или несколько `score_changed` с `data:{score}`, при необходимости
  `game_won`/`game_lost`, затем ровно один `session_ended` с `data:{}` на реальном
  финише. Общая форма event — `protocolVersion`, UUID v4 `eventId`, `sessionId`,
  `versionId`, последовательный `sequence`, `timestamp:Date.now()`, `type`, `data`.
- Счёт — целое число 0–1 000 000 000; больше — лучше. Финальный score_changed
  идёт перед outcome/завершением. Не более 20 событий/с и 1000 событий/попытку.
  После завершения новая попытка запускается кнопкой родителя, с новой сессией.
- HTML работает самостоятельно offline; отсутствие init отключает только
  телеметрию. Внутриигровые очки и конечное состояние остаются настоящими.

## Проверки и модель доверия

Игра остаётся в прежнем opaque `sandbox="allow-scripts"` с прежней `GAME_CSP`:
нет same-origin, сети, доступа к owner DOM/API, workers или внешним ресурсам.
Родитель проверяет `event.source`, origin `null`, channel, поля/размер события,
sessionId и versionId. HTTP forwarding выполняется только родителем, с очередью
до 128 событий. При ошибке показано отсутствие подтверждения; кнопка повторяет
точное событие с тем же eventId. Успех не выводится заранее.

На сервере проверяются cookie игрока, комната, версия, SHA256, токен попытки,
срок, sequence, timestamp, состояние и числовой диапазон. Прямого endpoint
«записать score в рейтинг» нет. Повтор точного event идемпотентен; изменённый
payload с тем же eventId, чужая попытка и новые события после финиша, замены
попытки, `game_error` или закрытия комнаты отклоняются. Кнопка «Остановить игру»
убирает iframe на этом экране; серверная попытка заканчивается при новой попытке
или по сроку, а уже отправленный HTTP-запрос может завершиться.
Завершение, результат попытки и улучшение рекорда сохраняются атомарно.

**Это не античит.** HTML и клиент выполняются у участника. Владелец изменённого
клиента/DevTools с собственными cookie и токеном может подделать весь корректный
поток событий. Сервер не способен доказать, что произвольный клиентский HTML
посчитал очки честно. `client_game_events` — явная граница доверия; рейтинг
подходит для доверенного LAN-демо, не для денежных призов или соревнований
с противником. Авторская игра проверена реальными браузерными действиями;
универсальная игровая корректность произвольного LLM HTML не заявлена.

LAN listener имеет явный allowlist: вход/личность/одна версия/попытки/events/
рейтинг выбранной комнаты и два статических assets. Нет owner API, jobs,
ChatGPT, библиотеки, других игр, экспорта БД, backup, `.env` или файлового сервера.
Host/Origin/forwarded guards остаются; POST требует точный Origin. QR-secret
идёт во fragment, удаляется из адресной строки и передаётся в ограниченном
join body. Каждый участник получает отдельную HttpOnly SameSite=Strict cookie.
Все поля ников в UI отображаются через textContent.

Ограничения MVP: 100 комнат, 100 игроков/комнату, 10 000 попыток; 128 TCP
соединений, HTTP/header timeout 5 с, keep-alive 1 с. Жизнь комнаты 2 часа,
попытки 10 минут; новая попытка не чаще раза в секунду, до 20/мин на игрока.
Входы ограничены 120/мин на listener, события 240/10 с на игрока, все запросы
12 000/мин на listener; тела join до 512 байт, event до 4096, ник 2–24 символа.
Повторное использование ника без его cookie запрещено. Числа — ресурсные caps,
не доказанная вместимость физических телефонов. Действуют также общие квоты
существующего Store: 10 000 sessions и 100 000 events на всю БД, включая обычные
игры; доступное число новых Arena-попыток может быть меньше. История не удаляется
автоматически.

SQLite v3 — добавочная миграция трёх Arena-таблиц и индексов; рекорд — поле игрока.
До обновления
v2 создаётся проверенный `before-v3-*.sqlite` в существующем backup-каталоге.
Старые версии/игры/jobs/events и `.env` сохраняются. До отката к старому бинарнику
нужна отдельная проверенная старая БД; версия 2 не откроет schema 3.

и всей Git-истории не нашёл утечек. Снимки ведущего и WebKit 390 просмотрены.

- API/SQLite: миграция v2 с snapshot, рекорды, реальные restart/reopen, атомарность
  при отказе SQLite, точные повторы, чужие сессии/версии, диапазон/размер/Origin,
  десять отдельных HTTP cookie и attempts; события в unit тестах синтетические.
- Browser E2E: создание authored игры через библиотеку, декодирование одного QR,
  десять contexts с касаниями и независимыми настоящими партиями, лучшие/худшие
  повторы, сетевой обрыв перед финалом, повтор отправки, штатный рестарт процесса,
  чтение и возобновление рейтинга. Без подстановки score в API или игровое состояние.
- Responsive: 320/360/390/430, tablet, desktop, Chromium/WebKit/Firefox по
  существующей матрице; реальные устройства и их вместимость **NOT_VERIFIED**.
- Hosted Actions остаются выключены по MICRO-019; hosted Windows/Ubuntu
  **NOT_VERIFIED**. LIVE inference/OAuth **NOT_RUN** (бюджет не запрашивался).

Команды: `npm run check`, `python scripts/check_repo.py`, `git diff --check`,
`.local/tools/gitleaks.exe git --redact --no-banner`. Отдельно быстрый сценарий:
`node scripts/browser-tests.mjs test tests/arena.spec.ts --project=chromium-desktop`.
Tests используют собственные временные БД и listener-порты, не загружают `.env`
и не подключаются к пользовательской БД. Gitleaks проверяет отдельно историю Git
и снимок отслеживаемых исходников с новыми файлами Arena, без ignored данных.
Снимки — в `.local/playwright-results`.

## Read-only источник идей и перспективы

Прочитаны `D:\21%\FinPlay_0_00_0\app\server.py` и templates join/host/leaderboard.
Переиспользованы идеи одного входа, персональной идентичности и polling.
Опасное различие: FinPlay вычисляет score своим серверным Python-движком;
произвольный HTML YAPLIX так проверить нельзя. Общие синхронные раунды, публичный
leaderboard без авторизации, Python production server и вставка ников через
innerHTML не переносились. FinPlay не изменялся.

Только перспективы: публичный HTTPS server, устойчивая идентификация,
масштабирование/уборка истории, серверно проверяемые правила или replay для
конкретных игр, античит и сетевой multiplayer. В MVP это не реализуется;
VPS, новые облачные сервисы и платные зависимости не добавлены.
