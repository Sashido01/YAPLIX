# Командная разработка YAPLIX

Команда — три человека. Доступ к Private-репозиторию выдаёт владелец после согласования; новый участник принимает приглашение и настраивает свой клон по [development-setup.md](docs/development-setup.md). Не храните в репозитории личные контакты и приватные настройки участников.

## Ветки и коммиты

`main` содержит стабильные изменения. Новую задачу обсудите в Issue или внутри команды; согласуйте область работы, чтобы не редактировать одни и те же файлы одновременно. Используйте `feature/<topic>`, `fix/<topic>`, `chore/<topic>` или `docs/<topic>` (латиница, короткое имя с дефисами). Существующие `feat/`-ветки допустимы.

При чистом рабочем дереве:

```sh
git status --short
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feature/game-generator
```

Делайте небольшие логичные коммиты: feat:, fix:, docs:, test:, chore:. Добавляйте явно проверенные файлы; перед коммитом смотрите git diff --cached. Секреты и посторонние изменения в коммит не включайте.

**Запрещены:** прямой push, force-push и удаление main; переписывание опубликованной общей истории, включая force-push в рабочую ветку. Не используйте reset --hard и clean для разрешения конфликтов. Локальная защита и её ограничения описаны в [github-ruleset.md](docs/github-ruleset.md).

## Обновление своей ветки и конфликты

Сначала закончите текущий локальный шаг и проверьте git status. При незакоммиченной работе сохраните её осознанно в своей ветке; не запускайте merge поверх неизвестных изменений.

```sh
git fetch origin
git merge origin/main
```

В совместной ветке сначала получите также изменения коллег: `git merge origin/<your-branch>`, затем `git merge origin/main`. Для общей истории используем merge, а не rebase.

При конфликте изучите обе версии, согласуйте смысл с автором соседнего изменения, удалите маркеры конфликта, выполните проверки и добавьте только разрешённые файлы через `git add <file>`. Завершите merge командой `git commit`. Если продолжать нельзя, `git merge --abort` отменяет текущий merge; перед ним убедитесь, что новая работа сохранена. Конфликт не решается принудительным push.

## Pull Request и review

После локальных проверок отправьте **свою ветку** и откройте PR в main:

```sh
git push -u origin HEAD
```

В GitHub выберите base: main, заполните [шаблон PR](.github/pull_request_template.md), укажите задачу, результат и фактически выполненные проверки. Назначьте одного из двух других участников reviewer. Reviewer проверяет корректность, понятность, безопасность, границы задачи и достоверность результатов. Автор исправляет замечания новыми коммитами; новый push требует повторной проверки.

Перед merge обязательно:

- Получить одобрение хотя бы одного другого участника на **последнюю версию** изменений; разрешить замечания и конфликты.
- Дождаться успешного CI для актуального PR: `repository-checks (ubuntu-24.04)`, `repository-checks (windows-latest)` и `secret-scan`. Ошибка, отмена или пропущенная проверка не являются успехом.
- Проверить отсутствие секретов, обновление документации и тесты, соответствующие изменению.
- Если main изменилась после проверки, обновить ветку через merge и повторить CI/review по затронутым изменениям.

Объединяйте через GitHub PR, предпочтительно **Create a merge commit**, чтобы сохранить индивидуальные коммиты. Пока серверное ограничение недоступно, соблюдение этих правил контролирует команда вручную; отсутствие блокировки кнопки Merge не даёт разрешения обходить процесс.

## Проверки и безопасность

Из корня проекта выполните python scripts/check_repo.py и python -m unittest
discover -s scripts/tests -v; на Ubuntu замените python на python3.
После npm ci и установки browser profiles выполните npm run check.
Это typecheck, API/SQLite/adapter integration и Playwright Chromium/WebKit.
Gitleaks, API-контракты и настройка — в [development-setup.md](docs/development-setup.md).

Не добавляйте API-ключи, токены, пароли, .env, персональные данные, внутреннюю переписку и неразрешённые материалы кейсодателя. Private не делает хранение секретов безопасным. Настройки храните локально, шаблоны — без реальных данных. Проверяйте лицензии сторонних материалов. Об утечках сообщайте приватно по [SECURITY.md](SECURITY.md); историю автоматически не переписывайте.

В [AUTHORS.md](AUTHORS.md) фиксируем только подтверждённый вклад с согласия участника. Соблюдайте [правила взаимодействия](CODE_OF_CONDUCT.md).
